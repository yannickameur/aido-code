# Session contract (M2)

The functional contract for M2 ("Sessions and resume"). See
`M2_SPEC.yaml` for the acceptance criteria this contract must satisfy,
`ARCHITECTURE.md`'s "Hard invariant (M2)" for the resume/run
separation, and `docs/CLI_SPEC.md`'s M2 section for the exact command
surface. Not implemented yet — this is what the governed WorkItem Flow
(`aido.m2.example.yaml`, WI-M2-01 through WI-M2-10) builds against.

## In one sentence

A session is AIDO Code's own frontend UX state — never a `Project`, an
`MVP`, a `WorkItem`, an `ExecutionRecord`, a `WaitRecord`, or a
replacement/copy of any orchestrator persistence. It records how a user
has been interacting with AIDO Code and which project it points at; it
is never authoritative for what the engine itself has done or decided.

## Stored fields

| Field | Description |
|---|---|
| `schema_version` | Integer, incremented on any breaking change to this shape. Never inferred from file structure. |
| `session_id` | Stable, opaque, unique, serializable identifier — see "Session identifier" below. |
| `created_at` | Timezone-aware timestamp, set once, never changed. |
| `updated_at` | Timezone-aware timestamp — see "When `updated_at` changes" below. |
| Project/config binding | Directory + exact `aido.yaml` path — see "Project binding" below. |
| Interaction history | See "Interaction history" below. |
| Display metadata | Only what's genuinely necessary to resume correctly (e.g. active display mode); kept minimal, nothing speculative for M3+. |

### Session identifier

`session_id` is stable (never regenerated for the same session), opaque
(carries no embedded meaning a caller should parse, e.g. never
`"<project_id>-<n>"`), unique (a UUID4 or equivalent), and serializable
(a plain string, safe to print, log, pass on a command line). It is
never derived from `project_id`, `mvp_id`, `work_item_id`, a provider
name, or a worker id — a session outlives, and is entirely independent
of, any specific engine identity.

### Path safety (DR-4)

`session_id` is generated by AIDO Code itself (a UUID4 or equivalent, so
by construction already a safe filename component), but `resume <id>`
takes an id from the **user** — a command-line argument or REPL input.
Before that id ever touches the filesystem:

- **Format validation first.** `<id>` is checked against the same
  strict, opaque format AIDO Code generates (e.g. UUID4's exact shape)
  *before* any path is constructed or any disk access happens. An id
  that fails this check is rejected with a clean "invalid session id"
  error — never passed through to a path lookup on the chance it might
  resolve to something.
- **Confinement, not trust.** A resolved session path is never built by
  blind string concatenation (`sessions/<user-input>`) — the final,
  resolved path is verified to still be a direct child of the sessions
  directory before it is opened. This is defense in depth on top of
  format validation, not a replacement for it.
- **Symlinks are never followed for session I/O.** If
  `sessions/<session_id>.json` (or `index.json`) is found to be a
  symlink, AIDO Code refuses to read or write through it — a clean,
  explicit error, never silent traversal to wherever the link points.
  AIDO Code itself never creates a symlink in this directory.
- **A moved/deleted bound project never triggers a search.** See
  "Project binding" below — this is the same fail-closed principle
  applied to `aido.yaml`, not just to the session file itself: AIDO
  Code never goes looking for "a similar project" as a fallback.

### When `updated_at` changes

"Most recently used" (`--continue`/`-c`, and the interactive picker's
own ordering) means *successfully opened or resumed*, not merely
*received a command*. `updated_at` is bumped on session creation
(`/new`), on every successful resume (`resume`, `resume <id>`,
`--resume`/`-r`, `--continue`/`-c`, `/resume`), and on every subsequent
interaction-history write — so a session the user opened and then
immediately exited (no command typed) still counts as the most recently
used one. Ties (identical `updated_at`, e.g. two sessions resumed within
the same clock tick) break by `session_id`, never by filesystem
iteration order — deterministic and covered by a test either way.

### Interaction history

M2 comes before M3 (natural-language piloting): its history is a plain,
structured record, never a "conversation" and never involving an LLM.
Each entry records: the user command (`/status`, `/workers`, ...), the
rendered result (or a structured reference to it, never a lossy
re-summary a later reader could mistake for the real thing), a
timestamp, and the input type (REPL command, CLI flag, ...). M3 may
later extend this same model to natural-language requests; M2 itself
introduces no LLM, no natural-language interpretation, and no new
authority over project state.

**Never stored, in a session file or its interaction history, under any
circumstance** (see "Secrets" below for the general rule this makes
concrete): a process environment variable or dump of `os.environ`; an
API key, token, or credential of any kind; raw provider stderr/stdout; a
raw subprocess log of any kind. Only what a frontend genuinely needs to
redisplay a past result is stored — `OrchestratorEngine`'s own typed,
already-secret-safe snapshot DTOs (`ProjectStatusSnapshot`,
`WorkerSnapshot`, ...), or a structured reference to one, never an
arbitrary object dump. This is a distinct concern from terminal
rendering safety (control-character/ANSI sanitization, M1.3's own
WI-M1.3-02): sanitizing what reaches the terminal never substitutes for
never persisting a secret in the first place, and persisting only safe
data never substitutes for sanitizing it again at render time — a
session file is not itself a trusted-safe-to-print source merely
because nothing secret is in it.

## Storage

Persistence belongs entirely to AIDO Code. It never uses, reads, or
writes any of `ai-dev-orchestrator`'s own SQLite files or its state
directory.

**Location**: `$XDG_STATE_HOME/aido-code/`, falling back to
`~/.local/state/aido-code/` when unset — mirroring the engine's own
P12 default-state-dir convention, but under this project's **own**
directory, never inside `~/.local/state/ai-dev-orchestrator/`. Sessions
live at `sessions/<session_id>.json`, plus a small index
(`sessions/index.json`: id + `updated_at` per session) — enough for the
most-recent-session rule (`--continue`/`-c`) and the interactive picker
without reading every session file on every invocation. All session
file access — read and write — is confined to this directory; see
"Path safety" below for how that confinement is enforced, not just
assumed.

**Format (KISS/YAGNI)**: one versioned JSON file per session. M2's
actual needs (read one session by id, list a small local index, detect
corruption, evolve the schema) don't require SQLite's transactional or
relational features at a single local user's session count. If a real,
demonstrated need appears later (very large session counts, real
concurrent-access patterns this can't safely satisfy), that becomes a
separate, evidenced decision, not built now.

**The index is a derived cache, never a second source of truth (DR-1)**:
each session's own file (`sessions/<session_id>.json`) is authoritative.
`sessions/index.json` exists purely as a fast lookup for the
most-recent-session rule and the interactive picker — it is always
rebuildable from the session files themselves (scan `sessions/*.json`,
read `session_id`/`updated_at` from each). If the index is missing,
corrupt, or found to disagree with a session file it references (e.g. a
stale `updated_at`), it is silently rebuilt from the real session files
on next access — never treated as itself authoritative, and never a
reason to fail a resume that the session file alone can satisfy.

**Atomic writes (stdlib only, DR-1)**: every write to a session file or
to `index.json` follows the same pattern — serialize to a temporary
file in the *same* directory as the target (so the later rename stays
within one filesystem), `flush()` the file object and `os.fsync()` its
descriptor, then `os.replace(tmp_path, target_path)` (POSIX-atomic
rename; the target is never observed by a reader in a partially-written
state). No new dependency: `tempfile`/`os.fsync`/`os.replace` from the
standard library are sufficient and are the only mechanism used.

**Corruption**: a session file that fails to parse as JSON, or fails
basic schema validation (missing field, unreadable `schema_version`),
is reported as a clean, explicit error naming the session id and the
problem — never silently dropped, never silently "repaired," never
treated as if it didn't exist. (The index, unlike a session file, *is*
silently rebuilt when found inconsistent — see above; that is not an
exception to this rule, since the index is never authoritative in the
first place.)

**Secrets**: a session file never contains an API key, token, or
credential of any kind — see "Interaction history" above for the full,
explicit never-stored list (DR-5).

## Commands

Current, pre-M8 binary name throughout (`docs/CLI_SPEC.md`).

| Command | Behavior |
|---|---|
| `aido-code resume` | Interactive picker over the session index |
| `aido-code resume <id>` | Direct resume of that exact session |
| `aido-code --resume <id>` / `-r <id>` | Aliases of direct resume |
| `aido-code --continue` / `-c` | Resumes the single most recently *used* session (latest `updated_at` in the index; ties break by `session_id`, never filesystem order). Fails explicitly if no session exists, rather than silently creating one. |
| `/resume` | Same picker, invoked from inside a running session |
| `/new` | New session: fresh `session_id`, attached to the detected project if one exists (else created unbound), empty interaction history, no engine-side `Project`/`MVP`/`WorkItem` created |

## Hard safety rule

**Resume never calls `OrchestratorEngine.run()`, probes or selects a
worker, or mutates engine state** — see `ARCHITECTURE.md`'s "Hard
invariant (M2)". Every command in the table above is session-level
only: it restores or creates AIDO Code's own UX state and nothing
about the engine's.

## Project binding

A session stores a stable reference to the project it is attached to:
the project directory and the exact path to the `aido.yaml` used. On
resume, this association is restored as-is. The SessionStore never
duplicates `ProjectConfig` (project/worker registry contents) inside a
session, and never copies engine state into it — a session only ever
points at where the configuration lives, read fresh (via
`OrchestratorEngine.open(...)`) when actually needed.

If the bound project directory or `aido.yaml` no longer exists, resume
fails cleanly with an explicit, actionable error naming the missing
path, consistent with this project's and the engine's own fail-closed
convention. AIDO Code never silently recreates the project or guesses
a replacement path. A degraded read-only mode (opening a session for
its own interaction history only, explicitly labeled) is a reasonable
future refinement, not required or built by M2 (YAGNI).

## Unbound sessions (DR-6)

**AIDO Code must be able to start without any `aido.yaml` in the
current directory.** `aido-code` (no project detected), `aido-code
resume`, `aido-code -c`, and the REPL's `/new`/`/help` all work with no
project bound — this is required, not merely tolerated, precisely so a
user can launch AIDO Code from an arbitrary directory and pick or
create a project-bound session afterward.

A session created this way (`/new` with no `aido.yaml` detected in the
working directory) is **`UNBOUND`**: its project/config binding is
explicitly absent, not a placeholder pointing at a guessed or default
project. `resume`/`--continue`/`-c`/`/resume` restore whatever binding
state a session already had, bound or unbound — resuming never
*changes* a session's binding.

Any command that genuinely needs a project (`/status`, `/workers`,
`/validate`, `/run`, ...) issued from an unbound session responds with a
clean, explicit "no project bound" message (a consistent, documented
wording — never a stack trace, never a silent no-op). It never:

- crashes;
- invents/fabricates a project;
- searches the filesystem for an `aido.yaml` it might mean;
- causes a provider call or touches the engine in any way.

Resuming a session that *is* bound restores its exact recorded
project/`aido.yaml` path, as already specified in "Project binding"
above — unbound is a distinct, legitimate, first-class state, never an
error condition by itself.

## Concurrency (DR-2)

M2 does not require a distributed system or a session broker/server —
explicitly not built. The minimal contract, fail-closed:

- Two processes must never be able to write the same session file
  concurrently and produce a torn/inconsistent result.
- **Mechanism, concretely — not a vague "lock file"**: a real OS-level
  advisory lock held on the session's own lock file for the duration a
  session is open, acquired non-blocking. On the platforms this project
  actually targets (Linux/macOS), that is the standard library's
  `fcntl.flock()` (`LOCK_EX | LOCK_NB`) — a kernel-held lock, not merely
  the *existence* of a file on disk. A second process attempting to
  open the same `session_id` while it is locked fails explicitly —
  "session `<id>` is already in use by another process" — rather than
  silently attaching to it or corrupting it.
- **Stale locks after a kill are resolved by construction, not by a
  cleanup step.** Because the lock is kernel-held against the process's
  own open file descriptor, the OS releases it automatically the moment
  that process dies for any reason — clean exit, crash, or `SIGKILL`.
  There is no separate "is this lock stale?" check to get wrong, and no
  window where a killed process's lock file lingers and blocks a
  legitimate new session open.
- **Cross-platform note**: `fcntl` is POSIX-only. If Windows support
  ever becomes a real, demonstrated product requirement, the options
  (stdlib `msvcrt.locking()` directly, vs. one small, mature
  cross-platform library such as `portalocker`) are evaluated then,
  against that real need — not spent effort here for a platform this
  project does not currently target (YAGNI; see also P16,
  `ai-dev-orchestrator`'s own `ROADMAP.md`).
- No server, no cross-machine coordination, no queueing: a single-user,
  local-filesystem contract only.
- **Tested with two real, independent processes** (WI-M2-09), not only
  simulated lock contention within one test process — the actual
  scenario this contract exists to prevent.

## What is never stored

The SessionStore must never persist any of the following as a source
of truth: WorkItem status, MVP status, `WAITING`/`RECOVERY_REQUIRED`,
`ExecutionRecord`, quota state, QA verdict, merge state — all of this
belongs to the engine alone.

A session's interaction history may retain a *display record* of a
past `/status` result (what was shown, when) — but any **current**
question about project state must go through `OrchestratorEngine`
again, never be answered from a session's own cached copy. A session is
a UX log, never a second engine.
